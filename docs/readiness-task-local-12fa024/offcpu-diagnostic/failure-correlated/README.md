# Correlated failed intervals: local scheduling service

This 120.109-second diagnostic uses the same diagnostic binary as allocation-natural. It does not change the official library, workload size, observers or 100 ms budget. It records allocator boundaries, stage CPU/wall time and 10 ms buffered per-thread/process counters together. It produced 60 capture Deadlines and 2 query Deadlines, business errors zero. Post-Deadline destruction is excluded from failure interval analysis.

There are 144 selected pre-Deadline intervals, with 339 thread state observations, all state 1. 111 intervals have an expanded process-counter bracket with zero page faults and all sampled thread states 1. Within those intervals, 54 successive sample pairs show unchanged thread CPU, up to 28.894 ms apart. These are measured gaps, not inferred from the host CPU utilization.

A failed query scan interval lasted 39.352 ms, consumed 0.042083 ms CPU, made no measured allocator calls, and had zero process faults/pageins/COW faults across the enclosing bracket. Three snapshots reported state 1; two were 12.142 ms apart without CPU advancement. The scanned path operates on an immutable snapshot without application locks, I/O or sleeps. Another failed validation interval lasted 90.336 ms with 3.573416 ms CPU, 0.028375 ms allocator time, zero faults and seven state-1 observations.

The local failure mechanism is therefore strongly supported as insufficient CPU scheduling service while the wall-clock deadline continues. This is substantially stronger than the earlier off-CPU-only inference. Apple XNU maps TH_RUN to TH_STATE_RUNNING (state 1), and reports waiting separately: https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/thread.c (retrieve_thread_basic_info). This published source explains the state interpretation; it is not a build-exact audit of the installed kernel. State 1 must not be described as proof the thread was executing on a CPU.

Limits: 10 ms snapshots can miss intervening waits. Positive process faults in other intervals cannot be assigned to this thread. The diagnostic adds allocator timing/checkpoints and a sampler; it establishes this local mechanism, not a zero-overhead performance result. It cannot retrospectively classify all CI failures. No claim is made that a particular competing process caused these delays.

Corrective boundary: do not switch the deadline to CPU time, increase the budget, add retries to hide failed attempts, or raise library thread priority globally. These would change the contract or application scheduling policy. No library correctness fix is justified by the correlated evidence. The practical correction must address execution/measurement isolation and demonstrate the same mechanism in CI before changing acceptance environment. Prior failures remain failures. Final acceptance and release remain blocked; no endurance rerun was launched.
