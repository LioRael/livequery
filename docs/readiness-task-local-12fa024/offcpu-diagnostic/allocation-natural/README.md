# Allocator boundary diagnostic (not acceptance)

Official library source remains 12fa024. The isolated copy wraps System allocator operations, records per-thread call count/wall time/slow-call count, and captures these counters at capture/query checkpoints. Records flush on thread exit. No external profiler is involved. Patch and binary hash define this diagnostic binary; report source_ref is not its complete provenance.

Two native unit tests passed (accounting a controlled delay, forwarding zeroed allocation/reallocation while preserving bytes). The delay fixture tests accounting, not a real malloc lock wait. A 96-byte allocator microbenchmark found approximately 47–64 ns extra per allocation/free. This is not zero overhead or end-to-end overhead validation. The first compile failed on a missing Debug derive, then passed after correcting it; native absolute toolchain invocation bypassed the mise cargo wrapper.

The 120.008-second natural workload recorded 87 capture Deadlines, zero business errors and one query Busy. All 87 failures have phase/allocator evidence; no buffered events were dropped. Twenty-five selected pre-return intervals exceeded 50 ms with allocator wall time under 10% and CPU under 20%. A validation interval was 216.603 ms wall / 4.257458 ms CPU / 0.162292 ms in allocator calls. Thus allocator contention cannot be the sole explanation of this run. Allocator wall time includes descheduling inside the allocator, so large allocator times do not establish lock contention either. Deadline-to-end intervals include snapshot destruction after the budget was already exceeded; do not mislabel these as the initiating cause.

Host activity was sampled by process name and CPU, without arguments. Concurrent compilation, filesystem scans and desktop activity were present. This is evidence of concurrent work, not attribution of a particular failure. Original CI failures remain unexplained.

A standalone control performed 200 windows of 1 ms CPU arithmetic without LiveQuery, locks or allocation; maximum wall time 2.962 ms. It ran later and cannot rule out earlier pressure. A further single 60.014-second correlated diagnostic added a 10 ms buffered thread-state sampler and a simultaneous arithmetic control (about 2% of one core). It had no Deadline and three slow captures. One validation interval was 37.240 ms wall / 3.414958 ms CPU / 0.010958 ms allocator time. Two snapshots 12.064 ms apart showed state 1 with only 16 us of accumulated CPU advancement. This is consistent with limited CPU service between samples, but snapshots cannot exclude intervening waits. The arithmetic control max was 17.138 ms wall / 1.001083 ms CPU, without a matching Deadline. These controls are not a fix or release acceptance.

No library fix is justified yet. Do not change wall-clock budget to CPU time or increase the timeout. Do not restart Instruments. The remaining distinction is scheduler service versus kernel/page-fault waits during the failed intervals; short passing controls do not resolve it. Preserve both red and green diagnostics and their observer overhead. No further workload is running.
