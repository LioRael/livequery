# Off-CPU diagnostic, not release evidence

Base source remains 12fa024. Modified diagnostic binaries are identified by each run's provenance and instrumentation patch. Official library source and 100 ms gate are unchanged.

The natural-id64 300-second run had no Deadline: business errors 0, query Busy 1, publication errors 0. Four internal capture spans were 52.878–76.361 ms. Largest gaps occurred both during row construction and validation. Sparse thread-state snapshots do not establish whether the thread was blocked or runnable without CPU. They cannot establish the cause of earlier Deadline failures.

The initial probe wrote slow records synchronously before capture returned. Consequently outer capture durations include diagnostic output overhead absent from internal span duration. These measurements must not be used as uninstrumented performance results. The buffered revision retains at most 256 slow events per thread and writes them on thread exit, reporting dropped events. Checkpoint and allocation overhead still exists.

Controlled SIGSTOP injection verifies clock/thread correlation only, not the natural bug. injection-id64 records the original probe. injection-buffered records the buffered probe: 171.813 ms checkpoint gap, 0.058 ms CPU, 20 matching samples. Neither is acceptance evidence.

Earlier Python monotonic origins and thread-handle identifiers did not match Rust CLOCK_MONOTONIC / pthread_threadid_np. The sampler here uses libc CLOCK_MONOTONIC and PROC_PIDTHREADID64INFO. State 1 is not proof of execution on CPU; state 3 is not a specific blocking cause. Raw aligned samples are gzip-compressed without changing their contents.

System Trace capability was separately verified against /bin/sleep: it exports Runnable, Running, Blocked and Interrupted context-switch events. The bounded 120-second buffered run completed with 23 capture Deadlines and 6 query Deadlines, business errors zero. However, the driver timed out after waiting 60 seconds for trace finalization; the trace document is incomplete and export fails with Document Missing Template Error. There is no usable scheduler evidence from that run. Failure phases and original workload results are preserved under system-trace-buffered. These failures occurred under tracing overhead and do not establish the cause of earlier untraced failures. The driver now records workload completion separately and waits for trace finalization without that timeout. No endurance retry is authorized before diagnosis and repair.

A subsequent bounded 45.017-second acquisition recorded zero errors and one slow capture (58.823 ms total; validation interval 52.364 ms / 5.126 ms CPU). The target has exited. xctrace PID 55710 remains processing/saving a large approximately 17 GB trace under target; do not start another acquisition. Its context-switch data is not yet export-verified. This is not a fix or release acceptance. Full System Trace is expensive on this traffic; future instrumentation design must bound trace volume and assess observer overhead. ## Cross-thread analysis of retained failed spans

`system-trace-buffered/cross-thread-stalls.json` analyzes the existing 120-second diagnostic; it does not run a workload. Its 29 failed spans have largest gaps in multiple phases: query sort/project (1), query scan (5); capture row construction (9), validation (12), and deadline-return cleanup (2). Fifteen query/capture checkpoint interval pairs overlap by at least 20 ms while each interval consumes less than 20% wall time in thread CPU; largest overlap is 103.085 ms. These are interval overlaps, not proof that both threads were off CPU at exactly the same instant. They argue against selecting a single row/validation CPU hotspot as a sufficient explanation. Shared allocator/kernel waits, scheduling and tracing disturbance remain distinguishable hypotheses, not established causes. Heavy tracing was active and its scheduler artifact failed, so this cannot identify the earlier uninstrumented failure root cause.

Before any new workload, validate a lower-overhead, bounded recorder on a controlled blocking example. Require a verified file-size/free-space guard throughout collection AND finalization, bounded capture duration, identifiable thread/clock references, and successful export of blocking stacks or scheduler transitions. Preserve capture and query separately. Do not use another passing short run as evidence of repair, and do not change the 100 ms budget.

This confirms the local comparison was not isolated from other benchmark/profiler activity. It does not correlate a particular Deadline with a recording: the original slow-capture records have no absolute timestamps. It does not explain CI failures, establish Tokio or scheduler causation, or invalidate the retained failed acceptance verdict. Future causal diagnostics require host-activity recording and independently timed capture/query failures; another endurance run is not the next step.

## Fault-counter probe preparation

Added a read-only proc_pidinfo(PROC_PIDTASKINFO) probe using the local SDK 96-byte proc_taskinfo layout. A controlled 16 MiB mmap touch increased faults by 1024 with pageins unchanged; 1000 reads averaged 4.906 microseconds. This validates demand-fault sensitivity, not detection of a disk wait. Counters are process-wide: no increment across a correctly bracketed interval can constrain the fault hypothesis, but an increment cannot identify the affected thread or prove a stall cause. thread-sampler-faults.py adds these counters to existing 10 ms buffered samples; no LiveQuery workload was run with this revision. Keep total_user/system as raw SDK values, not assumed nanoseconds. Original deadline cause remains unresolved.
